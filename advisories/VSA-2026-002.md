\# Vanguard Security Advisory: VSA-2026-002

\*\*Title:\*\* Heuristic Path-Validation Limitations and Inconsistent Socket Pinning in Tool Implementations  

\*\*Target Framework:\*\* CrewAI / `crewai-tools`  

\*\*Author:\*\* Triju Das, Vanguard Cyber Defense  

\*\*Classification:\*\* CWE-22 (Improper Limitation of a Pathname), CWE-918 (Server-Side Request Forgery), OWASP LLM08 (Excessive Agency)  

\*\*Status:\*\* Responsible Disclosure Draft / Research Report  



\---



\## 1. Executive Summary



During an architectural source-code audit of the `crewai-tools` library (`src/crewai\_tools/security/safe\_path.py` and associated tool modules), Vanguard Cyber Defense identified multiple structural inconsistencies and heuristic edge cases in the defensive validation layer:



1\. \*\*Heuristic File-Path Classification Gap:\*\* In `rag\_tool.py`, input strings are conditionally routed to `validate\_file\_path()` only if they contain path separators (`/`, `\\`), leading dots (`.`), or absolute paths. Bare filenames in the working directory bypass the security check.

2\. \*\*Permissive Default Scoping:\*\* The core `validate\_file\_path()` utility defaults its base boundary to `os.getcwd()` if no explicit directory is provided, permitting read operations across the application's root directory.

3\. \*\*Inconsistent Enforcement of Transport Pinning:\*\* While CrewAI implemented a socket-pinning mechanism (`safe\_requests.py` / `safe\_get`) to prevent DNS rebinding and redirect-based SSRF, only a small subset of URL-handling tools utilize this adapter; other tools rely solely on pre-fetch string validation via `validate\_url()`.



\---



\## 2. Technical Breakdown



\### Issue A: Heuristic Path-Detection Bypass in `rag\_tool.py`

\* \*\*Location:\*\* `lib/crewai-tools/src/crewai\_tools/tools/rag/rag\_tool.py` (lines \~330–345)

\* \*\*Finding:\*\* The condition checking whether an input is a file path requires a slash, a leading dot, or an absolute path. Bare filenames (e.g., `config.yaml`, `credentials.json`) evaluate to `False`, bypassing path validation entirely.



\### Issue B: Working Directory Scope in `safe\_path.py`

\* \*\*Location:\*\* `lib/crewai-tools/src/crewai\_tools/security/safe\_path.py` (lines \~85–95)

\* \*\*Finding:\*\* When tools call `validate\_file\_path()` without specifying a sandbox directory, the base directory defaults to `os.getcwd()`, allowing access to the root application directory where configuration and environment files reside.



\### Issue C: Inconsistent SSRF Protection

\* \*\*Location:\*\* `lib/crewai-tools/src/crewai\_tools/tools/`

\* \*\*Finding:\*\* Socket pinning via `safe\_get` is only enforced on three scraping tools (`scrape\_website\_tool.py`, `scrape\_element\_from\_website.py`, `url\_read\_tool.py`). Other URL-fetching tools only use string-level hostname checks via `validate\_url()`, leaving them open to DNS rebinding or redirect-based network traversal.



\---



\## 3. Recommended Hardening Guidelines



1\. \*\*Use Explicit Path Resolvers:\*\* Replace string-matching heuristics in `rag\_tool.py` with `pathlib.Path` existence checks so all local files are validated regardless of formatting.

2\. \*\*Define Sandboxed Root Paths:\*\* Avoid defaulting `base\_dir` to `os.getcwd()`. Require an explicit, sandboxed directory for all agent file operations.

3\. \*\*Standardize on `safe\_requests`:\*\* Route all URL-consuming tools through the socket-pinning transport layer rather than relying on string pre-checks alone.
